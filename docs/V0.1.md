# v0.1 最小验证场景与分阶段验收草案

状态：待实现、待试验的范围建议，不代表已经约定完整实现方案。本文按[驻项目安全专家的定位](VISION.md)拟定。

## 首版要回答的问题

一个 agent 能否通过持续研究和专家反馈，逐渐成为某个项目、某个安全方向上懂攻也懂防的合作伙伴？

首版可以缩小到一个明确版本和一个安全主题，例如权限隔离或某个关键模块。研究对象使用[标准项目安全工作区](WORKSPACES.md)，包含必要的主体、框架和依赖仓库及各自版本；涉及跨层安全时不能只看一个仓库。产品的长期责任对象仍是整个项目；缩小研究范围是为了能分步验收。

同一主题应覆盖两个方面：项目使用哪些机制提供保护、这些保护如何生效；攻击者可能在哪些条件下突破它们。即使样本没有漏洞，也应能展示可靠的机制理解与有效合作。

最小场景不是做一次审计后结束，而是跨越多次研究与交互：

```text
研究项目的一个安全主题并保留证据
  → 用户提问，利用已有理解回答
  → 遇到未知，与用户共同研究
  → 专家订正，更新相关知识
  → 新问题或新 commit 到来，继续利用并复查积累
```

## 第一条可演示的故事

1. 给定一个项目、固定版本、研究主题和资源预算，agent 自主阅读相关代码与历史，保存安全机制、威胁路径、证据和疑问。
2. 用户分别提出防护问题和攻击问题，例如“租户隔离怎样生效、需要哪些配置”和“新导出入口可能绕过哪些检查”，agent 给出带代码依据、适用条件和未知点的回答。
3. 用户提出尚未研究的新问题，agent 明确缺口，继续调查，必要时提出具体问题，并与用户共同推进。
4. 专家纠正一项重要前提，agent 更新该知识及相关判断；后续回答能够体现这次订正。
5. 提供一个相关的新 commit，agent 判断哪些既有知识可能受影响，读取新旧代码并复查结论，包括防护的增强、削弱或适用条件变化。

这些步骤可以分批实现和展示，不要求第一轮就具备全自动分支监测、所有外部工具或完整管理界面。第一版必须有实际的研究与积累，不能仅靠预先写好的知识演示问答。

## 分阶段验证

| 阶段 | 最小交付 | 重点检验 |
| --- | --- | --- |
| 1. 建立安全理解 | 一个主题的防护机制、威胁路径与待查问题 | 是否理解保护目标、实现、启用条件和局限；结论能否追溯到实际版本和材料 |
| 2. 带着积累合作 | 多次提问、未知问题调查与专家订正 | 是否利用此前研究；是否真正吸收反馈；问题是否得到推进 |
| 3. 跟随变化更新 | 相关 commits 到来后复查知识 | 能否识别受影响的防护、前提和旧代码，包括风险消除与防护失效 |
| 4. 扩展研究来源 | 引入历史漏洞、修复或外部可比实现 | 能否理解防护设计与漏洞根因，并区分相似性与实际适用条件 |

每个可用增量先用开源同类项目和外部 AI 算力检验，再尽早进入内部项目和内部算力环境。无需等所有阶段完成才进行内部试用；内部检验尤其需要观察业务背景缺失、专家时间和稀缺算力的影响。

## 如何验收

选取一组能由代码、历史材料或专家判定的问题，同时覆盖机制解释、设计或配置判断、攻击路径分析、未知问题合作，以及被订正或被版本变化影响的结论。

至少应包含一项有效防护、一项依赖配置或部署条件的保护，以及一条需要继续核实的潜在绕过路径。检查 agent 能否区分“机制存在”“已启用”“覆盖当前路径”和“仍未确认”，不能把每道题都引向漏洞报告。

关注以下结果：

- **回答质量**：是否正确，证据和适用版本是否可靠，是否把未知误说成确定结论。
- **防护理解**：能否解释保护目标、实现与启用方式、覆盖范围、失效边界和权衡，避免把局部防护泛化成整个项目安全。
- **合作能力**：能否将模糊问题转化为具体调查，提供有价值的中间发现，提出必要且具体的问题。
- **积累效果**：后续调查能否复用已有成果，避免反复询问相同背景，并正确使用专家订正。
- **更新能力**：重要前提被修改后，是否能识别相关知识需要复查，避免继续使用过期结论。
- **安全价值**：是否帮助团队正确理解和使用防护、作出安全设计判断，找到关键约束、严重风险线索或问题，并认真处理反证。
- **投入成本**：研究耗时、模型调用成本、专家交互时间，以及用户需求的响应时间。

对照应包括现有可用的 agent 或 multi-agent 方案。分别观察不提供历史积累、提供相同历史材料，以及由本原型持续维护积累的效果；保留研究与维护知识的成本，避免只计算最后一次回答的耗时。

样本应包含未见过的新问题，不能只问 agent 刚刚整理过的笔记。使用开源历史案例时也不能仅凭命中公开答案证明研究能力，需要检查证据过程，并尽早用内部项目检验。

当前先确定可复查的小规模案例，不预设检出率、响应分钟数或知识数量目标。

## 首版边界

知识与研究结果关联确定版本；项目变化后保留旧结论的适用范围。全量代码可作为研究上下文，但不宣称已全面理解或检查。

目标怎样构建和运行也是安全研究的一部分。工作区的 runtime/ 逐步记录配套版本、软硬件、有效配置、启动与最小业务用例，区分文档方案、构建成功、启动成功和真实路径跑通。可以先确认条件与缺口，再复用已有环境推进实验；目录和脚本存在不代表目标已经可运行。

用户当前需求优先，后台研究在可恢复的边界调整；中断后保留已取得的证据、未解决问题和后续方向。

发现问题后的动态验证、PoC、专门的准确率提升流程等按需调用已有系统。自动修复、合并阻断、运行时防护和大规模多项目并行不作为当前首版的必需交付。

机制解释、设计评估与加固建议属于专家能力；实现新的防护系统或自动操作生产配置不作为当前首版的必需交付。
