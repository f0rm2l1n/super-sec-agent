# 产品愿景：驻项目安全专家

状态：根据当前讨论整理的产品设想，待原型与实际使用验证，不代表已经实现的功能。

## 1. 我们希望它是谁

为每个项目配一位长期参与、懂攻也懂防的安全专家。

它不再只是某个任务的完成者，而是一个能够积累大量项目安全知识的长期伙伴：能基于证据回答用户问题；即使暂时回答不了，也能与用户一起研究和解决新问题。

它的责任对象是指定项目及关注的版本、分支。它既研究攻击面、漏洞和攻击路径，也研究产品的安全目标、防护设计、实现与部署条件，在安全设计、开发、部署、审计、渗透测试和漏洞研究中提供帮助。

它应能回答“哪里可能被攻破”，也应能回答“项目如何保护关键资产、为什么采用这些机制、怎样正确启用，以及保护在哪些条件下不再成立”。理解防护不是为了凑出一个漏洞结论；解释已有效的机制、明确覆盖范围和帮助团队正确使用这些机制，本身就是职责。

项目安全知识不是附带生成的文档，而是这个专家日后作出判断、提出问题和参与调查的基础。积累的价值体现在能否帮助解决实际问题，而不只是笔记数量。

## 2. 为什么需要这样一个角色

深入理解项目安全需要大量时间：阅读底层代码、理解业务前提、还原防护设计及其权衡、追溯漏洞和修复历史、研究相似实现，并不断跟上代码变化。一个人的时间有限，许多值得研究的方向无法持续投入。

内部代码与文档尤其需要从实际材料中获得理解，不能依赖模型已有知识。模型可以提供通用安全经验，但关于本项目的结论仍需从代码、文档、历史和专家反馈中建立证据。

我们希望 agent 持续承担这些研究工作，并保留研究过程，使项目每次安全行动都能利用此前的积累。用户也能随时加入，补充背景、纠正理解，或提出新的调查目标。

## 3. 它要积累哪些安全知识

| 研究方向 | 需要形成的理解 |
| --- | --- |
| 安全目标与威胁模型 | 关键资产是什么，要抵御什么能力的攻击者，哪些保证属于产品承诺，哪些属于环境前提 |
| 攻击面与信任边界 | 哪些主体能控制哪些输入；输入如何进入关键操作；权限、租户和进程边界在哪里 |
| 产品安全机制 | 认证授权、数据与进程隔离、加密与密钥管理、输入校验、内存保护、资源限制、安全默认值和审计等机制的目标、实现与协作关系 |
| 关键模块与底层机制 | 解析器、内存与对象生命周期、并发和状态管理等机制如何工作，依赖哪些安全前提 |
| 防护的覆盖与局限 | 机制在哪些入口生效、是否默认启用、配置和版本差异、例外路径、失效方式，以及相关证据和测试 |
| 历史漏洞与修复 | 漏洞根因、触发条件、影响路径、修复方式、适用版本，以及类似问题可能出现的位置 |
| 部署与防护运用 | 部署方式、业务规则、配置和构建选项如何影响保护；哪些加固建议适用，如何观察机制是否工作，以及哪些条件不能仅从源码确认 |
| 外部同类项目与模块 | 可比实现使用了哪些防护；外部 CVE、补丁和设计经验是否适用于本项目，哪些差异使其不适用 |
| 尚未解决的问题 | 当前假设、支持证据、反证、缺失信息和下一步调查方向 |
| 代码演进的影响 | 新 commits 如何改变攻击面、安全前提及历史结论，包括对未修改旧代码的影响 |

阅读普通项目知识是研究的必要部分，但研究方向应由安全问题牵引。已有项目知识库可以作为输入，不必重新建设一套通用项目知识挖掘系统。

对一项安全机制，应尽量建立“保护目标 → 设计理由 → 实现路径 → 启用条件 → 覆盖范围 → 局限与证据”的理解。需要区分设计上存在、代码中实现、特定部署中启用，以及对某条路径确实有效；不能看到一项机制就推断所有入口都安全。

## 4. 它平时做什么

在用户设定的项目范围、权限和资源预算内，它持续选择有价值的安全问题开展研究，包括攻击可行性和防护有效性，也包括尚未发现漏洞时对关键安全机制的系统理解。

研究线索可以来自关键模块、历史漏洞、修复补丁、外部类似实现、新 commits、用户提问或专家订正。它需要根据当前理解判断先研究什么、需要查阅哪些材料、什么时候换方向，以及什么时候值得请教专家。

一个可能的研究过程是：

```text
发现安全知识缺口或收到新线索
  → 结合历史积累提出问题与假设
  → 阅读代码、历史和外部资料，按需调用已有工具
  → 收集证据与反证，必要时向专家提问
  → 更新结论、适用条件和未解决问题
  → 根据结果决定后续研究
```

这不是要求每轮机械执行相同步骤。暂时没有答案、已有假设被否定或需要等待用户补充，都是可以保留并继续推进的研究状态。

优先级首先考虑潜在严重安全影响、关键保护机制的重要性、相关路径的可达性、知识缺口及用户当前需求。低安全影响代码不应占用大量深度研究资源；但不能仅凭目录、改动行数或提交标题认定没有安全价值。研究阻止严重问题发生的机制，同样属于高价值工作。

常驻意味着能持续接收变化、保留状态并继续工作，不意味着持续满负荷消耗算力。资源不足时应保存进度并等待可用预算。

## 5. 用户如何与它合作

用户可以直接提问、提出调查目标、补充材料、纠正知识，或调整研究优先级。用户需求应优先得到响应；耗时调查需要说明当前证据和推进状态。

| 用户需求 | 期望的专家行为 |
| --- | --- |
| “这个模块的权限检查在哪里？” | 用当前版本的代码与已有积累解释机制、入口及适用条件 |
| “项目有哪些租户隔离机制，分别保护什么？” | 解释各层保护及其依赖，指出已确认的覆盖范围和未知部分 |
| “开启这个安全选项能防住什么，会影响哪些功能？” | 根据实现与文档说明保护效果、必要条件、局限和兼容性或性能权衡 |
| “这个新功能应复用哪些现有防护？” | 找到可用的机制与接入要求，说明需要核实的覆盖路径和设计约束 |
| “拿到普通用户权限后，跨租户风险先查哪里？” | 给出有依据的调查入口、相关历史与待确认路径 |
| “这个外部 CVE 对我们有没有启发？” | 理解根因和安全约束，比较本项目的等价路径及差异 |
| “最近这批提交是否改变了安全边界？” | 结合新旧代码与历史理解，识别需要重新评估的前提 |
| “你的结论不成立，线上还有一层隔离。” | 记录条件和来源，检查依赖旧结论的其他知识，并按需核实实现 |
| “这里我们都不知道，一起查一下。” | 明确未知点、制定可调整的调查计划，分工收集证据并持续交换发现 |

回答不了时，需要区分缺少业务背景、缺少源码或配置、证据互相矛盾，以及仍需实验确认等情况。能够自行调查的部分继续推进；需要人的信息则提出具体问题。一次没能回答，不应让研究历史丢失。

用户与 agent 都可能出错。专家反馈是重要依据，但仍需注明适用条件；与代码或其他证据冲突时应保留冲突并进一步核实。

## 6. 知识如何积累、订正和更新

需要保留的不只是最后一句结论，还包括它为什么成立，以及什么变化可能让它失效：

- 对应的项目版本、配置或部署前提。
- 安全机制保护的目标、设计理由、启用方式、覆盖范围和局限；设计理由不明时保留未知，不能凭实现编造意图。
- 相关文件、函数、提交、外部材料或专家反馈。
- 已确认的事实、暂定判断、风险假设与未解决的问题。
- 支持与反对该结论的证据，以及后续调查的原因。
- 与其他知识和调查之间的依赖关系。

例如，“所有写操作都经过租户校验”被专家订正后，不能只修改这一条笔记。需要继续检查引用该前提的其他结论，判断哪些调查需要恢复。

新 commits 也会触发同样的问题：改动可能发生在入口或配置中，却改变了旧代码的可信输入前提；新增防护也可能消除旧风险或改变推荐配置。需要保留历史结论适用的版本，并在当前版本重新核实，避免把过期理解继续作为事实使用。

定期或按事件进行反思与整理，可以用于发现矛盾、合并重复知识、清理过期结论、重新安排研究方向。具体触发方式与资源安排属于后续实现选择，不预先固化为某一种 agent loop。

## 7. 从理解防护到共同研究的合作场景

以下是期望行为的示例，不是已实现的 demo。

用户先问：“后台导出靠什么保证租户隔离，部署时要注意什么？”

专家利用此前积累，解释接口授权、任务中的租户上下文、数据查询约束和部署隔离如何共同提供保护，给出代码和配置依据，并区分产品内建保护与环境提供的保证。关于某层保护缺少证据时，明确保留未知。

用户接着问：“最近新增了批量导出，普通用户能否借它跨租户读取数据？”

它结合防护知识与相关修复历史，检查新入口是否正确复用了这些机制，指出尚未核实的路径，并继续调查。用户补充生产环境的队列隔离方式后，它调整原有假设，区分代码路径与实际部署条件。需要实验时，接入已有验证能力或与用户分工执行。

最终可以形成有条件的安全解释、部署或设计建议、值得继续检查的风险候选，或证据充分的安全问题。无论是否发现漏洞，本次研究得到的机制、入口、约束、反证和未解决问题都会成为下一次合作的基础。

之后出现新的调用入口或部署变化时，它应能识别相关性并复查这段理解。

## 8. 产品边界与技术路线

计划基于 DeepSeek Super-agent 构建常驻工作、用户交互和调查延续的基础。需要验证的核心能力是：持续选择有价值的安全研究方向、积累并校正项目知识，以及利用积累与人共同解决问题。

Super-agent 与 multi-agent 可以同时使用。常驻、记忆、多 agent 或角色提示词本身都不能证明产品优势；需要通过真实研究和用户合作来检验。

已有项目知识系统、安全审查器、CVE 分析工具、代码搜索和验证系统均可作为能力来源。暂不绑定某一个审查引擎，也不将本项目定义为某个工具的调度外壳。

动态验证、PoC、专门的准确率提升流程等复用已有能力。本项目不因需要交付一个完整专家体验，就重复开发这些执行系统。

懂防包括理解和评估现有机制，协助安全设计、加固和配置决策。它不意味着首版就要开发防护产品或自动更改生产配置；建议与实际执行需要区分，并说明依据、适用条件及权衡。

## 9. 如何判断它是否有用

应关注长期积累是否改善后续工作：回答是否准确、有依据且说明不确定性；新问题是否能够推进；专家订正是否真正被吸收；版本变化后是否能发现知识失效；研究员是否减少了重复解释和定位代码的时间。

尽早识别严重安全问题仍是重要目标，但知识价值不能只按漏洞数量衡量。准确解释安全机制、帮助团队正确启用防护、评估设计权衡、排除错误假设和找到高价值调查入口，都应计入价值。需要同时观察攻击研究与防护理解，避免只奖励“发现漏洞”而诱导误报。
